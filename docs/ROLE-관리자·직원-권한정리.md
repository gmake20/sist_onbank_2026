## 2. 역할 한글 정리

### 관리자 (`admin` 테이블, `/admin/**`): 시스템·감독 업무

| 역할 | 한글 이름 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| `SUPER_ADMIN` | 총괄 관리자 (1명) | 관리자(OPERATOR·SERVICE)·직원 계정 생성, 권한 변경, 잠금 해제, 직원 계정 관리, 지점/ATM 관리, 활동 로그·로그인 이력 조회. 아래 두 역할의 업무도 모두 가능 | 대출·카드 심사 |
| `OPERATOR` | 운영 관리자 | 이상거래(FDS) 처리, 실시간 모니터링, 회원·계좌·거래 전체 조회, 이상거래 대응 중 계좌 동결, **계정 잠금 해제·임시 비밀번호 재발급** (SUPER_ADMIN 계정 재발급은 제외) | 계정 생성·권한 변경, 활동 로그, 공지 관리, 심사 |
| `SERVICE` | 고객지원 관리자 | 공지사항·FAQ 관리 | 회원·계좌·거래 조회, 이상거래, 심사 |

> `SERVICE`는 원래 "상품·고객지원 관리자"였습니다. README 8-1장에서 상품 관리가 직원(MANAGER) 업무로 옮겨갔기 때문에 "고객지원 관리자"로 바꿔 적었습니다. 맡는 일이 공지·FAQ만 남아서 역할을 따로 둘지는 다시 판단해야 합니다 (6장).

### 직원 (`employee` 테이블, `/employee/**`): 창구 업무

| 역할 | 한글 이름 | 하는 일 |
|---|---|---|
| `STAFF` | 일반 직원 (창구) | 회원·계좌 조회, 고객·계좌를 검색한 뒤 거래 조회, 본인확인 심사, 1:1 문의 답변, 대출·카드 심사 접수(1차 의견) |
| `MANAGER` | 책임자 | STAFF 업무 전부 (`RoleHierarchy`: `ROLE_MANAGER > ROLE_STAFF`) + 승인 업무: 대출·카드 최종 심사, 계좌 동결·해제, 이체한도 증액, 상품 관리, 카드 정지. 이상거래 알림 받기·조회 |

**나누는 기준 (직무 분리)**: 고객 업무를 **처리·승인**하는 사람은 직원이고, 그 처리를 **감독·기록 조회**하거나 시스템을 관리하는 사람은 관리자입니다. 관리자는 심사하지 않습니다. DB에서도 업무 처리자 컬럼(`reviewed_employee_id`)은 직원을, 이상거래 담당자 컬럼(`fds_detection.assigned_admin_id`)은 관리자를 가리킵니다.

## 4. 로그인: 겹치는 부분과 나누는 안

팀 README 12장에서 "고객·직원·관리자 로그인/로그아웃, `ADMIN` 엔티티·로그인"은 팀원1 담당입니다. 그런데 관리자 파트 문서(기능명세서 AUT-001)에는 "로그인 구현은 관리자 파트"라고 적혀 있어서 겹쳤습니다. **로그인은 팀원1 쪽으로 정리하고, 관리자 파트 문서를 고칩니다.**

| 항목 | 관리자 파트 문서 (이전) | 팀원1 현재 상태 | 나누는 안 |
|---|---|---|---|
| 로그인 화면·경로 | `/admin/login` 하나로 직원·관리자 공용, 통합 UserDetailsService | `/admin/login`(아이디) + `/employee/login`(사번), 화면은 `backoffice/login.html` 공용. 구현됨 | 팀원1 구현 사용 |
| 로그아웃 (AUT-002) | 관리자 파트 | `/admin/logout`, `/employee/logout`. 구현됨 | 팀원1 구현 사용 |
| 영역 접근 제어 (AUT-003) | 관리자 파트 | 필터 체인 3개로 영역 분리. 구현됨 | 팀원1 구현 사용 |
| 역할별 접근 제어 (AUT-004) | 관리자 파트 | `SecurityConfig`에 TODO만 있음 | 권한표(3장)는 관리자 파트가 정함. **코드를 누가 어디에 넣을지는 확인 필요** (6장) |
| 5회 실패 잠금 | AUT-001 처리 로직 | `auth.md` 3장 ⑤ "다음 단계", 세 영역 모두 같은 구조로 만든다고 적혀 있음. `Admin` 엔티티에는 아직 실패 횟수를 바꾸는 메서드가 없음 | 팀원1 핸들러에서 처리 |
| 마지막 로그인 일시 (`admin.last_login_at`) | AUT-001 처리 로직 | 아직 없음 | 팀원1 성공 핸들러에서 갱신 |

| 세션 타임아웃·중복 로그인 제한 | 없음 | `auth.md` 3장 ⑥ "다음 단계" (세 체인 모두) | 팀원1 |

## 5. 로그: 겹치는 부분과 나누는 안

로그는 **로그인 이력**과 **작업 이력** 두 가지입니다.

| 로그 | 테이블 (DDL 소유) | 기록하는 쪽 (안) | 조회 화면 (안) |
|---|---|---|---|
| 고객 로그인 이력 | `login_log` (팀원1) | 팀원1 로그인 핸들러 | 고객 본인: 보안설정 (팀원1) / 직원: 회원 상세의 로그인 이력 (관리자 파트, MEM-005) |
| 직원 로그인 이력 | `employee_login_log` (팀원1) | 팀원1 로그인 핸들러 | 관리자 활동 로그 화면의 "로그인 이력" (관리자 파트, SUPER_ADMIN) |
| 관리자 로그인 이력 | `admin_login_log` (관리자 파트) | **팀원1 로그인 핸들러** | 위와 같은 화면 |
| 작업 이력 (동결·심사·권한 변경 등) | `admin_log` (관리자 파트) | 상태를 바꾸는 기능이 `AdminLogService` 호출 | 활동 로그 화면 (관리자 파트, SUPER_ADMIN) |

**겹친 곳 1. `admin_login_log` 기록**
- 관리자 파트 문서(AUT 기능 문서, DECISIONS D-08)에는 "관리자 파트가 기록"으로, `auth.md` 3장 ⑤와 마지막 체크리스트 8번에는 "팀원1이 `login_log`·`employee_login_log`·`admin_login_log` 세 개를 기록"으로 되어 있습니다.
- 제안: **기록은 팀원1 핸들러에서 세 테이블을 같은 방식으로**, 테이블(DDL)과 조회 화면은 관리자 파트. `admin_login_log`는 `employee_login_log`와 모양을 맞춰 두었습니다. 실패 사유 값만 다릅니다 (`INACTIVE`).
- `admin_login_log`의 엔티티·Repository를 누가 만들지는 확인 필요 (6장).

**겹친 곳 2. `admin_log` 작업 이력**
- 팀원1이 `BackOfficeUser`(`getActorType()`, `getActorId()`)를 만들어 두었습니다. 관리자 파트는 이것으로 `admin_log.actor_type`, `actor_id`를 기록합니다.
- `auth.md` 3장 ⑧ 예시에 있는 `adminLogService.write(...)`는 **관리자 파트가 만듭니다** (LOG-001).
- 규칙: 직원·관리자가 고객 데이터의 상태를 바꾸면 `admin_log` 1건을 남깁니다. 팀원1이 제공하는 본인확인 승인·반려, 이체한도 승인도 직원 화면(관리자 파트)에서 호출하므로, 기록은 화면 쪽(관리자 파트)에서 하는 안을 제안합니다. 서비스 안에서 기록할지는 확인 필요.
- 로그인·로그아웃은 `admin_log`에 넣지 않습니다. 없는 아이디로 시도한 실패는 `actor_id`(NOT NULL)를 채울 수 없어서 로그인 이력 테이블로 따로 둡니다 (DECISIONS D-08).

## 6. 팀원1에게 확인할 것

1. **역할별 접근 제어 코드 위치**: 3장 표를 `SecurityConfig`의 URL 규칙으로 넣을지(팀원1 파일), 관리자 파트 컨트롤러에 `@PreAuthorize`로 넣을지.
2. **계좌 동결 권한**: MANAGER와 OPERATOR 둘 다 가능하게 하고 싶습니다. 이상거래 처리의 마지막 단계(사기 의심 조치)에서 관리자가 바로 동결합니다 (기능명세서 FDS 처리 로직). 기록은 `admin_log`의 actor_type으로 구분됩니다.
3. **대출 심사 2단계**: README 8-1장은 MANAGER만 심사하지만, 관리자 파트 안은 STAFF 접수 → MANAGER 최종입니다. 대출 담당(팀원3)과 상태값을 맞춰야 합니다.
4. **로그인 핸들러 범위**: 5회 잠금, `last_login_at` 갱신, 로그인 이력 기록을 관리자(`admin`)까지 해 주시는지. `admin_login_log` 엔티티·Repository는 누가 만들지.
5. **비밀번호 변경 화면**: 임시 비밀번호 강제 변경 화면을 직원·관리자 공용으로 팀원1이 만드는지, 관리자 파트가 만드는지.
6. **README 8-1장 "확정 필요" 항목**: 카드 관리, 1:1 문의 답변, 거래 관리를 직원 영역으로 하는 것에 동의합니다. 단, 전체 거래 목록은 관리자만 봅니다.
7. **직원 계정 생성에 필요한 조회 (상의)**: 관리자 화면에서 총괄 관리자가 직원 계정을 만듭니다 (FUNC-ADM-ACT-005, 핵심, 회원가입 아님). 저장은 이미 있는 `Employee.builder()`(직원 등록용)와 `save()`를 그대로 씁니다. 다만 아래 세 가지는 팀원1 테이블을 읽어야 해서 어디에 둘지 같이 정하고 싶습니다.
   - **사번 자동 생성**: 시드와 같은 `E` + 4자리, 가장 큰 사번 +1 (`E0003` → `E0004`). 사번이 글자라 DB가 번호를 올려 주지 않아서, 가장 큰 사번을 한 번 조회해야 합니다.
   - **이메일 중복 확인**: `uk_employee_email` 때문에 같은 이메일이면 저장이 실패합니다. 저장 전에 확인해 "이미 등록된 이메일입니다"를 보여 주려고 합니다.
   - **소속 지점 드롭다운**: `branch_id`가 NOT NULL + FK라 지점을 골라야 저장됩니다. 지점(BRANCH, 사용 중) 목록을 보여 줄 조회가 필요한데 `branch` 엔티티가 아직 없습니다.
   - 위 조회를 `EmployeeRepository`(와 지점 쪽)에 넣어 주실지, 관리자 파트에 조회용으로 따로 둘지 의견 부탁드립니다.
8. **(요청, API를 처음 만들 때) `/admin/api/**`는 로그인 안 됐을 때 401로**: 관리자 화면에서 fetch로 부르는 데이터 API는 `/admin/api/**`에 둡니다(관리자 체인 안에 들어가도록). 지금은 로그인 안 된 요청을 전부 로그인 화면으로 보내서, fetch가 JSON 대신 로그인 화면 HTML을 받게 됩니다. `SecurityConfig.java` 60줄을 아래처럼 바꾸고 import 3줄(`org.springframework.http.HttpStatus`, `org.springframework.security.web.authentication.HttpStatusEntryPoint`, `org.springframework.security.web.servlet.util.matcher.PathPatternRequestMatcher`)을 추가하는 안입니다. 실행해 보지 않았으니 `BackOfficeLoginTests`에 "로그인 없이 `GET /admin/api/...` → 401" 테스트를 같이 넣어 주세요. 직원 쪽 API가 생기면 91줄에 `/employee/api/**`로 같은 설정을 넣습니다.
   ```java
   .exceptionHandling(ex -> ex
       .accessDeniedHandler(accessDeniedHandler("/admin/login"))
       .defaultAuthenticationEntryPointFor(
               new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED),
               PathPatternRequestMatcher.withDefaults().matcher("/admin/api/**")))
   ```
   참고: CSRF 토큰이 만료되면 151줄 설정이 로그인 화면(`?expired`)으로 보내므로, fetch로 상태를 바꾸는 API(POST·PATCH)를 만들 때 이 경우도 같이 정해야 합니다.
