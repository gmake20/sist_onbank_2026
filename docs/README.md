> 학원 파이널 프로젝트 | 팀원 4명 | Spring Boot 기반 모의 인터넷뱅킹 서비스

## 0. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 목표 | 실제 인터넷뱅킹 서비스를 참고한 **모의(가상) 인터넷뱅킹 서비스** 구현 |
| 팀 구성 | 4명 |
| 백엔드 | Java, Spring Boot, Spring MVC, Spring Security |
| 데이터 접근 | **Spring Data JPA** (복잡한 검색 조회는 JPQL, 필요 시 Querydsl) |
| DB | Oracle |
| 프론트 | **Thymeleaf** (서버 사이드 렌더링) + HTML / CSS / JavaScript |
| 통신 | Thymeleaf 화면 요청 + 비동기 처리가 필요한 기능(계좌주 확인, 알림 등)은 REST API(fetch) |
| 인증 방식 | Spring Security **세션 기반 로그인** (Thymeleaf SSR 구조에 맞춰 JWT 대신 세션 사용) |
| 형상관리 | Git / GitHub |
| 배포 | **AWS** (EC2에 Spring Boot 실행, DB는 AWS 상의 Oracle) — 상세는 [13-1장](#13-1-배포-aws) |

> **기술 스택 확정**: Spring Boot + Spring Data JPA + Thymeleaf 조합으로 확정합니다. (MyBatis, JSP는 사용하지 않음)

## 1. 프로젝트 컨셉 제안 (3가지)

### 컨셉 A. 개인용 인터넷뱅킹 (표준형)
일반 개인 고객이 사용하는 인터넷뱅킹을 그대로 축소한 형태. 회원가입, 계좌개설, 입출금, 이체, 거래내역, 예적금 가입까지 "은행다움"을 가장 직관적으로 보여줄 수 있는 컨셉.

### 컨셉 B. 개인+관리자 통합형 인터넷뱅킹 (관리자 콘솔 강화형)
컨셉 A의 기능에 더해 **은행 직원(관리자) 콘솔**의 비중을 크게 높인 형태. 고객 승인, 계좌 동결/해제, 이상거래 모니터링, 상품 등록/관리 등 운영자 관점 기능을 강화하여 백오피스 시스템까지 경험.

### 컨셉 C. 테마형 인터넷뱅킹 (특화 상품 중심형)
> ⚠️ **"컨셉 C(테마형 인터넷뱅킹)"는 실제 은행업계에서 쓰이는 공식 명칭이나 표준 분류가 아니라, 이 기획서에서 편의상 붙인 카테고리명**입니다. 다만 아래 개별 기능들은 실제 서비스에서 찾아볼 수 있는 것들을 참고했습니다 (예: 카카오뱅크의 "26주 적금", 토스뱅크의 "목표통장" → 적금 챌린지형 / 토스·뱅크샐러드의 소비 자동분류·리포트 기능 → 가계부 연동형 / 증권사 MTS·토스증권의 모의투자 기능 → 모의투자 연동형).

기본 뱅킹 기능 위에 하나의 특화 테마를 얹는 형태. 예를 들어:
- **적금 챌린지형**: 목표 저축, 자동이체 적금, 만기 시뮬레이션 등 적금 상품에 특화
- **가계부 연동형**: 이체/출금 내역을 자동으로 분류하여 소비 리포트를 제공하는 자산관리 기능 결합
- **모의투자 연동형**: 입출금 계좌에서 가상의 예수금으로 모의 투자(펀드 매수/매도)까지 확장

| 컨셉 | 주요 사용자 | 설명 |

## 3. 컨셉별 핵심 기능

### 컨셉 A. 표준형
- 회원가입 / 로그인 (본인인증 흉내: 휴대폰 인증 mock, 보안카드/OTP mock)
- 계좌 개설 (입출금 통장, 예금, 적금)
- 입금 / 출금
- 계좌이체 (본인 계좌 간, 타행/타인 계좌 이체)
- 거래내역 조회 (검색, 기간별 필터, 엑셀/CSV 내보내기)
- 예금 / 적금 가입 및 만기 처리
- 체크카드 신청/관리 (mock)
- 관리자: 회원/계좌 조회, 상품 관리

### 컨셉 B. 관리자 강화형
- 컨셉 A 전체 기능
- 관리자 승인 프로세스 (첫 계좌 개설 시 **본인확인(비대면 실명확인 mock) 심사** — 회원가입 자체는 승인 없이 즉시 완료)
- 계좌 동결/해제, 이체 한도 설정
- 이상거래 탐지 룰(예: 단시간 고액 이체) 및 알림
- 관리자 대시보드 (전체 회원수, 거래량, 상품 가입 현황 통계)
- **[확장] 대출 신청/심사**: 재직정보 등 간단 조건 입력 → **관리자 심사(승인/거절)** → 승인 시 대출금 입금 + 상환 스케줄 자동 생성
- **[확장] 실시간 알림**: 입출금/이체/대출 승인 발생 시 WebSocket 기반으로 화면에 즉시 알림 표시 (선택 구현, 어려우면 폴링 방식으로 대체)

### 컨셉 C. 테마형 (예: 적금 챌린지형)
- 컨셉 A의 계좌/이체/거래내역 기본 기능
- 목표금액/목표기간 설정 적금
- 자동이체(정기 적립) 스케줄링 + 배치 처리
- 목표 달성률 시각화(차트)
- 만기 시뮬레이션(이자 계산기)

## 4. 구현 난이도 구분

### 구현하기 좋은 기능 (난이도 낮음~중간, 학습효과 높음)
| 기능 | 비고 |
|---|---|
| 회원가입/로그인 | Spring Security 세션 기반 인증, 권한(Role) 학습에 적합 |
| 계좌 개설/조회 | 기본 CRUD + 계좌번호 생성 규칙 + 계좌 비밀번호 설정 정도로 구현 가능 |
| 입금/출금 | 잔액 검증 로직으로 트랜잭션 처리 학습 |
| 계좌이체 | **동시성 제어(비관적 락 + 락 획득 순서 고정) 학습 포인트**로 매우 좋음 |
| 계좌 비밀번호 검증/잠금 | 오류 횟수 누적 → 잠금이라는 은행 특유의 상태 전이를 간단하게 구현 가능 |
| 거래내역 조회 | 페이징, 검색, 정렬 등 Spring Data JPA(Pageable, JPQL) 쿼리 실습에 적합 |
| 예적금 가입 | 상품 마스터 테이블 + 가입 테이블 구조 설계 연습 |
| 관리자 기본 기능(회원/계좌 조회, 상태 변경) | 권한 분리(Role) 학습에 적합 |
| 마이페이지(비밀번호 변경, 회원정보 수정) | 기본기지만 필수 |
| 대출 신청/관리자 심사/상환 스케줄 계산 | 신용평가 없이 "신청 → 관리자 승인/거절" 상태 흐름으로 제한하면 난이도 적정, 상환 스케줄 계산 로직 학습에 좋음 |

### 구현 난이도가 높은 기능 (선택적으로만 도전)
| 기능 | 비고 |
|---|---|
| 실시간 이상거래 탐지 | 규칙 엔진 수준으로 간소화 필요 |
| 적금 자동이체 배치 스케줄러 | Spring Scheduler로 간소화하면 도전 가능 |
| OTP/생체인증 등 실제 보안 인증 연동 | mock으로 대체 권장 |
| 실시간 환율/타행 연동 | 외부 API 연동은 mock 데이터로 대체 |
| 대규모 동시성/부하 처리 | 학원 프로젝트 범위를 벗어남, 개념만 반영 |
| 모의투자/펀드 매매 로직 | 컨셉 C 선택 시 범위를 최소화해서 구현 |
| 실시간 알림(WebSocket/STOMP) | 새로운 기술 스택 학습이 필요하므로 핵심 기능 완료 후 여유 있을 때 도전. 시간이 부족하면 주기적 폴링(setInterval) 방식으로 대체 |

### 구현하지 않아도 되는 기능 (명확히 제외)
- 실제 금융결제원/오픈뱅킹 연동, 실제 계좌 실명 인증
- 실제 문자(SMS)/공동인증서/생체인증 연동 (전부 mock 처리)
- 실시간 대량 트랜잭션 처리, 장애 복구(HA), 다중 서버 분산 처리
- 외화 환전·외화 계좌, 보험 상품 등 수신·여신 외 금융업무
- 공과금/생활요금 납부 (전기·통신·지방세·관리비·지로) — 범위 확대를 피하기 위해 제외
- 대출의 신용평가(CB사 연동, 신용등급 산정), 담보/보증 심사, 등급별 금리 차등
  - ※ **대출 신청과 관리자 승인/거절 심사 자체는 확장 도메인으로 구현합니다**([5-1장](#5-1-기능-확장-대출--실시간-알림) 참고). 제외 대상은 실제 은행의 신용평가·담보심사 시스템입니다.
- PG사 연동 실제 결제

## 5. 최종 추천 컨셉: **컨셉 B (개인+관리자 통합형 인터넷뱅킹, 단 관리자 기능은 "적정 수준"으로 조정)**

### 추천 이유

**A안(순수 개인용)만으로는 4명이 나눠 맡기엔 업무량이 부족**합니다. 회원가입/로그인, 계좌, 이체, 거래내역, 예적금이 전부인데 이걸 4명이 나누면 한 사람당 파트가 너무 얇아져서 "각자 CRUD 화면 하나씩 만드는" 프로젝트로 전락하기 쉽습니다. 반대로 **C안(테마형)은 특화 기능(자동이체 배치, 모의투자 등)의 구현 난이도가 높아 일정 리스크가 크고**, 팀원 전원이 Spring Boot의 핵심(트랜잭션, 인증/인가, REST API 설계)을 고르게 경험하기보다 특정 파트에 난이도가 쏠릴 위험이 있습니다.

**B안**은 다음 이유로 4인 팀에 가장 적합합니다.

1. **업무 분담이 자연스럽게 4갈래로 나뉨**: (1) 인증/회원 (2) 계좌/입출금/이체 (3) 거래내역/예적금/카드 (4) 관리자 콘솔. 각 파트가 독립적인 도메인이면서도 서로 API로 연결되어 협업 경험을 쌓을 수 있습니다.
2. **은행 프로젝트다움이 확실히 드러남**: 단순 회원-게시판 CRUD가 아니라, "승인 프로세스", "계좌 상태(정상/동결)", "이체 한도" 같은 은행 도메인 특유의 상태(state)와 업무 로직이 들어가 포트폴리오에서 차별화됩니다.
3. **관리자 파트가 난이도를 스스로 조절 가능**: 이상거래 탐지 같은 고난도 기능은 "간단한 룰 기반"으로 낮추고, 승인/동결/통계 같은 실현 가능한 기능에 집중하면 일정 부담 없이 "규모 있어 보이는" 결과물을 만들 수 있습니다.
4. **보안/금융 특성을 자연스럽게 반영**: 관리자 승인 절차, 권한 분리(Role: USER/ADMIN), 계좌 동결 등은 실제 금융 서비스가 왜 이런 프로세스를 갖는지 이해하며 구현할 수 있어 학습효과가 큽니다.

즉, B안은 **"기능 개수"가 아니라 "도메인 상태와 업무 프로세스"로 프로젝트 규모를 키우는 방식**이라 학원 프로젝트 난이도를 벗어나지 않으면서도 포트폴리오 임팩트를 확보할 수 있습니다.

### 5-1. 기능 확장: 대출 + 실시간 알림

기본 뱅킹 기능(입출금/이체/예적금)만으로는 4명이 나눠 맡기에 파트가 얇다는 판단에 따라, 다음 두 가지를 **확장 기능**으로 추가합니다.

- **대출 도메인 추가**: 재직정보/희망금액 등 간단한 조건을 입력해 대출을 신청하면 **관리자가 신청 내용을 확인한 뒤 승인/거절**합니다. 승인 시 대출금이 지정 입출금 계좌로 입금되고 상환 스케줄(원리금균등상환 등)이 자동 생성됩니다. 새로운 도메인이 하나 늘어나 업무 분담에 여유가 생기고, 관리자 파트와도 자연스럽게 연결됩니다.

#### 대출 심사 프로세스 (관리자 승인 방식)

```
[회원] 대출 신청 (재직상태, 월소득, 희망금액, 기간, 상환방식, 입금받을 계좌)
   ↓  LOAN.STATUS = 신청(APPLIED)
[관리자] 대출 심사 관리 화면에서 신청 내역 확인
   │   - 시스템은 판단을 돕는 참고 정보만 표시 (예: 연소득 대비 희망금액 비율, 기존 대출 건수)
   │   - 자동 승인/거절은 하지 않으며 최종 결정은 관리자가 함
   ├─ 거절 → STATUS = 거절(REJECTED), 거절 사유 입력 필수 → 회원에게 알림
   └─ 승인 → STATUS = 승인(APPROVED)
            ↓ (하나의 트랜잭션)
         ① 대출금을 회원의 입금 계좌에 입금 + TRANSACTION_HISTORY 기록
         ② LOAN_REPAYMENT_SCHEDULE 회차별 생성
         ③ STATUS = 상환중(ACTIVE) → 전 회차 상환 시 상환완료(CLOSED)
         ④ ADMIN_LOG 기록, 회원에게 알림
```

- 대출 상태: `APPLIED(신청) → APPROVED(승인) → ACTIVE(상환중) → CLOSED(상환완료)`, 또는 `APPLIED → REJECTED(거절)`. 회원이 심사 전에 취소하면 `CANCELED`.
- 심사 이력을 남기기 위해 `LOAN`에 심사 관리자, 심사일시, 거절 사유를 저장합니다.
- **실시간 알림(WebSocket)**: 입출금/이체/대출 승인 시 화면에 즉시 알림이 뜨는 기능. 새로운 기술 스택(WebSocket/STOMP)을 경험할 수 있어 포트폴리오 임팩트가 크지만, 난이도가 있으므로 **선택 구현(스트레치 목표)**으로 분류합니다.

두 기능 모두 핵심 기능(회원/계좌/이체/예적금/관리자)이 안정적으로 완성된 이후에 시간이 허락하는 범위에서 진행하는 것을 원칙으로 합니다. 자세한 우선순위는 [6장](#6-기능별-구현-범위-제안)과 [14장 일정](#14-개발-순서-주차별-로드맵-총-7주-기준)을 참고하세요.

### 5-2. 회원가입 · 계좌 개설 프로세스 (본인확인 방식)

#### 실제 은행의 방식

실제 은행은 **"웹사이트/인터넷뱅킹 가입"과 "계좌 개설"이 별개 절차**이며, 직원이 회원가입을 하나하나 승인하지 않습니다. 사람(또는 시스템)이 엄격하게 확인하는 시점은 **계좌를 처음 만들 때의 실명확인**입니다.

| 구분 | 실제 은행 | 이번 프로젝트 |
|---|---|---|
| 회원가입 | 휴대폰 인증 등으로 본인 확인 후 즉시 완료 | 휴대폰 인증 mock 후 **즉시 정상(ACTIVE)** — 관리자 승인 없음 |
| 첫 계좌 개설 | 비대면 실명확인: 신분증 사본 제출 + 타행 계좌 1원 인증 / 영상통화 등 2가지 이상. 신분증 진위는 공공기관 시스템으로 확인, 직원이 검토하기도 함 | 신분증 정보 mock 입력 + 타행 1원 인증 mock → **관리자가 본인확인 심사 후 승인** |
| 이후 계좌 개설 | 실명확인된 고객은 추가 확인 없이 개설 | 본인확인 완료 회원은 **즉시 개설** |
| 대포통장 방지 | 입출금 계좌는 보통 20영업일 내 1개만 신규 개설 가능 | `[선택]` 동일 규칙 적용 (영업일은 주말만 제외하고 공휴일은 생략해 단순화) |

#### 프로젝트 적용 흐름

```
[회원] 회원가입 (휴대폰 인증 mock) → MEMBER.STATUS = ACTIVE, 실명확인상태 = 미확인(NONE)
   ↓  바로 로그인 가능 (상품 조회, 고객센터, 이자 계산기 등은 이용 가능)
[회원] 첫 입출금 계좌 개설 신청
   │   - 실명확인상태가 NONE/REJECTED이면 본인확인 단계를 거침
   │     : 신분증 종류, 신분증 발급일자(mock), 타행 계좌 1원 인증 mock
   │   - IDENTITY_VERIFICATION 1건 생성(PENDING), 회원 실명확인상태 = 확인대기(PENDING)
   │   - ACCOUNT 생성, 상태 = 개설대기(PENDING) — 계좌번호는 이때 발급하되 거래 불가
   ↓
[관리자] 회원 관리 > 본인확인 심사 목록에서 확인
   ├─ 승인 → 회원 실명확인상태 = VERIFIED, 대기 중 계좌 상태 = 정상(ACTIVE)
   │         ADMIN_LOG 기록, 회원에게 알림
   └─ 반려 → 회원 실명확인상태 = REJECTED(반려 사유 입력 필수), 대기 계좌 상태 = 개설거절(REJECTED)
             회원은 정보를 수정해 다시 신청 가능
   ↓
[회원] 본인확인 완료 후에는 추가 계좌 개설, 예적금 가입, 카드 신청, 대출 신청이 즉시 가능
```

**정책 요약**
- **본인확인 전 회원이 할 수 없는 것**: 입출금/이체(계좌가 없으므로), 예적금 가입, 카드 신청, 대출 신청. 이 검증은 각 Service에서 공통 메서드(`memberService.requireVerified(memberId)`)로 처리합니다.
- **첫 계좌는 반드시 입출금 계좌**입니다. 예금·적금 계좌는 입출금 계좌에서 돈을 옮겨 가입하므로, 본인확인이 끝난 뒤 상품 가입([8장](#8-전체-메뉴-구조)의 8.3)으로만 생성합니다.
- 주민등록번호 전체, 실제 신분증 이미지 등 **실제 개인정보는 저장하지 않습니다**. 신분증 정보는 형식만 갖춘 mock 값입니다.
- `[선택]` 대포통장 방지 규칙: 마지막 입출금 계좌 개설일로부터 20영업일 이내에는 새 입출금 계좌 개설을 거부하고 남은 기간을 안내합니다.

## 7. 실제 금융 서비스 vs 학원 프로젝트 구현의 차이

| 구분 | 실제 금융 서비스 | 이번 프로젝트 |
|---|---|---|
| 본인 인증 | 공동인증서, 생체인증, 본인확인기관 연동 | 아이디/비밀번호 + mock 인증(형식 검증 수준) |
| 계좌 개설 | 비대면 실명확인(신분증 진위확인 + 타행 1원 인증 등), 금융결제원 계좌 실명조회 | 첫 개설 시 신분증 정보·1원 인증 mock → 관리자 본인확인 심사 후 활성화, 이후에는 DB 내 규칙 기반 즉시 생성 |
| 보안 | HSM, 이상금융거래탐지시스템(FDS), 암호화 통신 인프라 | 비밀번호 암호화(BCrypt), HTTPS 흉내, 간단한 룰 기반 이상거래 체크 |
| 트랜잭션 | 분산 원장, 장애 복구, 이중화 서버 | 단일 서버 + DB 트랜잭션(ACID)만으로 정합성 보장 |
| 이체망 | 금융결제원 타행 이체망 연동 | 가상의 "타행"도 동일 DB 내 계좌로 처리(연동 없이 mock) |
| 카드 | VAN/PG사 실 결제 연동 | 카드 정보 관리(CRUD) 수준까지만 |
| 대출 | 신용평가시스템(CB사 연동), 등급별 금리 차등, 담보/보증 심사 | 재직정보/희망금액 등 단순 신청 정보를 관리자가 확인해 승인·거절, 단일 고정금리 상품 |
| 계좌 비밀번호 | 보안매체(OTP 등)와 함께 사용, 오류 누적 시 영업점 방문 해제 | 4자리 비밀번호 BCrypt 저장 + 5회 오류 잠금, 해제는 관리자 화면에서 처리 |
| 법적 규제 | 전자금융거래법 등 각종 컴플라이언스 | 규제 준수는 다루지 않고 **개념만 문서화**(발표 시 "실무에서는 이런 규제가 있다" 정도로 언급) |

> 포인트: **UX와 도메인 로직(상태, 프로세스)은 실제와 유사하게, 인프라/외부연동/규제는 전부 mock 또는 생략**하는 것이 이 프로젝트의 원칙입니다.

## 8. 전체 메뉴 구조

팀원 4명 모두 개발 경험이 있는 점을 고려해, 기존 뼈대(회원/계좌/이체/예적금/카드/관리자)에 **이체 심화(예약·정기이체, 즐겨찾기), 자산관리, 고객센터, 마이페이지 보안설정**을 추가로 반영했습니다. 실제 구현 시 우선순위를 바로 판단할 수 있도록 각 항목에 등급을 표기합니다.

> **표기 기준**
> - `[핵심]` — 반드시 구현 (이게 없으면 "은행 서비스"라 부르기 어려운 기능)
> - `[심화]` — 난이도가 낮은 편이라 우수한 팀이면 기본 포함을 권장하는 기능
> - `[선택]` — 기술적으로 도전적이라 시간이 허락할 때만 진행하는 스트레치 기능

### 8-1. 권한별 접근 범위 (Spring Security 설정 기준)

권한은 `ROLE_USER`, `ROLE_ADMIN` 두 가지입니다. URL 단위 접근 제어는 Spring Security 설정(`SecurityFilterChain`)에서, **본인확인 완료 여부**처럼 회원 상태에 따른 제한은 Service 계층(`memberService.requireVerified()`)에서 처리합니다.

| 기능 | 비회원 | USER (본인확인 전) | USER (본인확인 완료) | ADMIN |
|---|:---:|:---:|:---:|:---:|
| 메인, 회원가입, 로그인, 아이디/비밀번호 찾기 | O | - | - | - |
| 예적금 상품 조회, 대출 이자 시뮬레이터 | O | O | O | O |
| 공지사항, FAQ 조회, 지점/ATM 찾기 | O | O | O | O |
| 대시보드, 마이페이지, 보안설정, 알림 | X | O | O | X |
| 첫 입출금 계좌 개설 신청 (본인확인 포함) | X | O | - | X |
| 계좌 추가 개설, 입출금, 이체, 거래내역, 자산관리 | X | X | O | X |
| 예적금 가입, 카드 신청, 대출 신청 | X | X | O | X |
| 1:1 문의 등록/조회 | X | O | O | X |
| 관리자 메뉴 전체 (`/admin/**`) | X | X | X | O |

- **관리자 계정은 은행 직원용**이라 고객 금융 기능(계좌, 이체 등)을 사용하지 않습니다. 시연할 때는 고객 계정과 관리자 계정을 따로 사용합니다.
- URL 규칙 예시

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/", "/signup", "/login", "/find-id", "/reset-password",
                     "/products/**", "/loans/calculator",
                     "/support/notices/**", "/support/faq/**", "/branches/**",
                     "/css/**", "/js/**", "/images/**").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().hasRole("USER"));
```

> `/products/**`는 목록·상세 조회만 공개하고, 가입 요청(`/products/{id}/subscribe`)은 Controller에서 로그인과 본인확인을 추가로 검사합니다. 경로를 더 엄격히 나누고 싶다면 가입 경로를 `permitAll` 규칙보다 먼저 `hasRole("USER")`로 선언합니다.

> **계좌 비밀번호 보안 참고**: 4자리 숫자는 경우의 수가 10,000개뿐이라 해시만으로는 무차별 대입을 막을 수 없습니다. 실질적인 방어 수단은 **5회 오류 잠금**이므로, 오류 횟수 증가와 잠금 전환은 비밀번호 검증과 같은 트랜잭션에서 반드시 커밋되도록 구현합니다. (이체가 다른 이유로 롤백되어도 오류 횟수는 남아야 하므로 `REQUIRES_NEW` 전파 또는 검증 단계를 이체 트랜잭션과 분리)

## 11. 테이블 간 관계 설명 (ERD 설계 전 이해용)

- **MEMBER : ACCOUNT = 1 : N**
  한 회원은 여러 계좌(입출금/예금/적금)를 가질 수 있음. `ACCOUNT.MEMBER_ID`가 `MEMBER`를 참조.

- **MEMBER : IDENTITY_VERIFICATION = 1 : N, MEMBER(ADMIN) : IDENTITY_VERIFICATION = 1 : N** *(신규)*
  회원의 본인확인 신청 이력(반려 후 재신청 포함)을 기록. `IDENTITY_VERIFICATION.MEMBER_ID`가 신청 회원을, `REVIEWED_ADMIN_ID`(nullable)가 심사한 관리자를 참조. 최신 심사 결과는 조회 편의를 위해 `MEMBER.VERIFICATION_STATUS`에도 반영.

- **ACCOUNT : TRANSACTION_HISTORY = 1 : N**
  한 계좌에서 여러 건의 거래(입금/출금/이체)가 발생. `TRANSACTION_HISTORY.ACCOUNT_ID`가 `ACCOUNT`를 참조.

- **ACCOUNT : TRANSFER = 1 : N (양방향 참조)**
  이체는 출금계좌(`FROM_ACCOUNT_ID`)와 입금계좌(`TO_ACCOUNT_ID`) 두 개의 `ACCOUNT`를 참조. 하나의 `TRANSFER` 건은 출금 계좌/입금 계좌 양쪽에 각각 `TRANSACTION_HISTORY` 레코드를 1건씩 생성(더블 엔트리 방식 권장).

- **PRODUCT : PRODUCT_SUBSCRIPTION = 1 : N**
  하나의 예적금 상품에 여러 회원이 가입. `PRODUCT_SUBSCRIPTION`은 `MEMBER_ID`, `PRODUCT_ID`, `ACCOUNT_ID`를 모두 참조하는 교차 테이블 성격.

- **MEMBER : CARD = 1 : N**
  한 회원이 여러 장의 카드를 가질 수 있고, 카드는 특정 `ACCOUNT`(결제 연동 계좌)를 참조.

- **MEMBER : ADMIN_LOG = 1 : N**
  관리자(=MEMBER 중 ROLE이 ADMIN인 회원)가 수행한 작업 이력을 기록. `ADMIN_LOG.ADMIN_ID`가 `MEMBER`를 참조.

- **MEMBER : FAVORITE_ACCOUNT = 1 : N** *(신규)*
  회원 한 명이 여러 개의 즐겨찾기 계좌(자주 쓰는 이체 대상)를 등록. `FAVORITE_ACCOUNT.MEMBER_ID`가 `MEMBER`를 참조.

- **TRANSACTION_CATEGORY : TRANSACTION_HISTORY = 1 : N** *(신규)*
  거래내역 한 건은 하나의 소비 카테고리에 속함(미분류 허용). 자산관리 메뉴의 카테고리별 리포트 집계에 사용.

- **MEMBER : SCHEDULED_TRANSFER = 1 : N** *(신규)*
  회원이 등록한 예약/정기이체 목록. `SCHEDULED_TRANSFER.FROM_ACCOUNT_ID`가 `ACCOUNT`를 참조하며, 배치(Scheduler)가 주기적으로 조회해 실행 후 `TRANSFER`/`TRANSACTION_HISTORY`를 생성.

- **PRODUCT_SUBSCRIPTION : SAVING_GOAL = 1 : 1** *(신규)*
  적금 가입 건 하나에 목표저축 챌린지 정보가 1건 연결(선택 가입).

- **CARD : CARD_USAGE_HISTORY = 1 : N** *(신규)*
  카드 한 장에 여러 건의 사용내역(mock)이 기록됨.

- **MEMBER : NOTIFICATION_SETTING = 1 : N** *(신규)*
  회원별로 알림 유형(입출금/이체/대출/공지 등)마다 수신 여부를 설정.

- **MEMBER(ADMIN) : NOTICE = 1 : N** *(신규)*
  관리자가 작성한 공지사항 목록. `NOTICE.ADMIN_ID`가 `MEMBER`(ROLE=ADMIN)를 참조.

- **MEMBER : INQUIRY = 1 : N, MEMBER(ADMIN) : INQUIRY = 1 : N** *(신규)*
  회원이 작성한 1:1 문의(`INQUIRY.MEMBER_ID`)와 답변한 관리자(`INQUIRY.ANSWERED_ADMIN_ID`, nullable)를 각각 참조하는 이중 FK 구조.

- **MEMBER : LOGIN_LOG = 1 : N** *(신규 필수화)*
  회원의 로그인 시도 이력을 기록. 마이페이지 보안설정 화면(13.3)에서 본인 이력 조회.

- **MEMBER : LOAN = 1 : N, MEMBER(ADMIN) : LOAN = 1 : N** *(확장)*
  한 회원이 여러 건의 대출을 신청할 수 있음. `LOAN.MEMBER_ID`가 신청 회원을, `LOAN.REVIEWED_ADMIN_ID`(nullable)가 심사한 관리자를 참조하는 이중 FK 구조. `LOAN.DEPOSIT_ACCOUNT_ID`는 대출금을 받을 `ACCOUNT`를 참조.

- **LOAN : LOAN_REPAYMENT_SCHEDULE = 1 : N** *(확장)*
  승인된 대출 1건에 대해 회차별 상환 스케줄이 여러 건 생성됨. `LOAN_REPAYMENT_SCHEDULE.LOAN_ID`가 `LOAN`을 참조.

- **MEMBER : NOTIFICATION = 1 : N** *(확장)*
  회원 한 명에게 여러 건의 알림이 발생. `NOTIFICATION.MEMBER_ID`가 `MEMBER`를 참조하며, 입출금/이체(`TRANSACTION_HISTORY`)나 대출 승인(`LOAN`) 이벤트 발생 시점에 생성되는 파생 데이터 성격.

- **MEMBER.ROLE**
  단일 `MEMBER` 테이블에서 `ROLE` 컬럼(USER/ADMIN)으로 권한을 구분하는 방식을 권장(테이블을 분리하지 않아 단순함 유지).

> **설계 원칙 — 거래 원장과 잔액의 관계**
> - `TRANSACTION_HISTORY`는 **거래 원장**입니다. 한 번 기록된 거래는 수정·삭제하지 않고, 취소가 필요하면 반대 방향 거래를 새로 기록합니다.
> - `ACCOUNT.BALANCE`는 매번 원장을 합산하지 않도록 **현재 잔액을 저장해 두는 컬럼**입니다.
> - 잔액을 바꾸는 모든 처리는 **잔액 갱신과 원장 기록을 하나의 트랜잭션 안에서 함께** 수행합니다. 둘 중 하나라도 실패하면 전체를 롤백하므로, 트랜잭션 안에서 UPDATE와 INSERT 중 어느 것을 먼저 실행하는지는 정합성에 영향을 주지 않습니다.
> - 원장의 각 행에는 `거래 후 잔액`을 저장하고, **"계좌별 원장 금액 합계 = `ACCOUNT.BALANCE`"** 가 항상 성립해야 합니다. 이 검증 쿼리를 테스트 코드와 관리자 화면에 두면 정합성을 확인할 수 있습니다.

### 11-1. 입출금/이체 트랜잭션 처리 규칙

모든 입출금/이체는 Service 계층의 `@Transactional` 메서드 하나에서 아래 순서로 처리합니다.

```
1. 계좌 비밀번호 검증 (실패 시 오류 횟수 증가, 5회째에 LOCKED 전환 후 예외)
   - 오류 횟수 갱신은 이체 롤백과 무관하게 남아야 하므로 별도 트랜잭션(REQUIRES_NEW)으로 커밋
2. 관련 계좌를 비관적 락으로 조회
   - JPA: @Lock(LockModeType.PESSIMISTIC_WRITE) → Oracle: SELECT ... FOR UPDATE
   - 이체처럼 계좌 2개를 잠글 때는 반드시 "계좌 ID 오름차순"으로 잠금
3. 검증: 계좌 상태(정상 여부), 잔액, 1일 이체한도
4. ACCOUNT.BALANCE 갱신 (출금 계좌 차감, 입금 계좌 증가)
5. TRANSACTION_HISTORY 기록 (이체는 출금/입금 2건, 각각 거래 후 잔액 포함) + TRANSFER 1건
6. 커밋 → 커밋 이후 알림 이벤트 발행 (@TransactionalEventListener(phase = AFTER_COMMIT))
```

**데드락 방지 — 락 획득 순서 고정**

A→B 이체와 B→A 이체가 동시에 실행되면, 각 트랜잭션이 자기 출금 계좌를 먼저 잠근 뒤 상대 계좌를 기다리게 되어 **데드락**이 발생합니다.

```
트랜잭션1 (A→B): A 잠금 → B 대기 ⏳
트랜잭션2 (B→A): B 잠금 → A 대기 ⏳   → 서로 영원히 대기 (Oracle ORA-00060)
```

출금/입금 방향과 상관없이 **항상 계좌 ID가 작은 계좌부터 잠그면** 두 트랜잭션이 같은 계좌를 먼저 잡으려 경쟁하게 되므로 순환 대기가 생기지 않습니다.

```java
Long firstId  = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);
Account first  = accountRepository.findByIdForUpdate(firstId);
Account second = accountRepository.findByIdForUpdate(secondId);
// 이후 from/to를 구분해 출금·입금 처리
```

추가 규칙:
- 출금 계좌와 입금 계좌가 같으면 락을 걸기 전에 예외 처리합니다.
- 락 대기 시간 제한(`jakarta.persistence.lock.timeout` 힌트)을 두어 무한 대기를 막습니다.
- 3주차 이체 구현 시 **동시 이체 테스트**(`ExecutorService`로 A→B, B→A를 동시에 다수 실행)를 작성해 데드락이 없고 잔액 합계가 보존되는지 검증합니다.

- 지점/ATM은 **팀원1이 `BRANCH` 테이블과 조회 화면(41번)을 담당**하고, 관리자 지점/ATM 관리 화면(42번, 선택)은 팀원4가 팀원1의 Service를 호출해 구현합니다.
- 대출 심사는 **팀원3이 `LoanService.approve()/reject()`(대출금 입금 + 상환 스케줄 생성)를 제공**하고, **팀원4는 관리자 심사 화면에서 이를 호출**하는 방식으로 나눕니다. 대출금 입금은 팀원2의 입금 Service를 재사용합니다.
- 알림은 팀원2(계좌/이체)·팀원3(대출)이 발생시키는 이벤트를 팀원4가 구독해 전송하는 방식으로 협업 (예: 이체 완료 시점에 이벤트를 발행하면 팀원4의 알림 모듈이 이를 받아 `NOTIFICATION`을 생성).

## 13. GitHub 충돌 최소화 개발 방식

1. **브랜치 전략**: `main`(배포 가능 상태 유지) → `develop`(통합 브랜치) → 기능별 `feature/{파트명}-{기능명}` 브랜치. 각자 자기 브랜치에서 작업 후 `develop`으로 PR.
2. **패키지 구조로 물리적 충돌 최소화**: 도메인별 패키지(`member`, `account`, `product`, `admin`)를 처음부터 분리하여 각자 다른 파일/디렉토리에서 작업하도록 설계. 공통 파일(설정, 공통 응답 클래스)은 최소 인원(1명)만 수정 권한을 갖도록 규칙화.
3. **PR 리뷰 필수화**: `develop` 브랜치에 직접 push 금지, 최소 1명 이상 리뷰 후 머지.
4. **잦은 커밋 & 작은 단위 PR**: 기능 단위로 작게 쪼개 자주 머지하여 충돌 범위를 줄임.
5. **공통 파일 변경 시 사전 공지**: `application.yml`, `build.gradle`(or `pom.xml`), 공통 Entity/DTO 수정 시 팀 채널에 사전 공지 후 진행.
6. **이슈/칸반 보드 연동**: GitHub Issues + Projects(칸반)로 작업 항목을 트래킹하여 중복 작업 방지.
7. **커밋 컨벤션 통일**: `feat:`, `fix:`, `refactor:`, `docs:` 등 접두사 규칙을 초기에 합의.

### 13-1. 배포 (AWS)

최종 발표는 로컬이 아닌 **AWS에 배포한 서버**로 시연하는 것을 목표로 합니다. 담당은 팀원4(공통 인프라)입니다.

**기본 구성**
```
[브라우저] → [EC2: Spring Boot 실행 (java -jar)] → [Oracle DB]
                                                   ├─ 방법 1: Amazon RDS for Oracle
                                                   └─ 방법 2: 같은 EC2 또는 별도 EC2에 Oracle XE 설치(Docker)
```

| 항목 | 내용 |
|---|---|
| 애플리케이션 | EC2 인스턴스 1대에 빌드한 jar 실행. 필요 시 Nginx를 앞에 두고 80 → 8080 연결 |
| DB | 비용과 학원 계정 조건에 따라 RDS for Oracle 또는 EC2 + Oracle XE 중 선택. **착수 전에 프리티어/크레딧 적용 범위와 인스턴스 메모리를 반드시 확인** (Oracle XE는 메모리를 많이 쓰므로 가장 작은 인스턴스에서는 부족할 수 있음) |
| 설정 분리 | `application-local.yml`(개발) / `application-prod.yml`(배포)로 프로필 분리, 실행 시 `--spring.profiles.active=prod` |
| 비밀정보 | DB 비밀번호 등은 **Git에 커밋하지 않고** EC2 환경변수로 주입 (`.gitignore`에 로컬 설정 파일 추가) |
| 보안그룹 | 웹 포트(80/8080)만 외부 공개, DB 포트(1521)는 애플리케이션 서버에서만 접근 허용, SSH(22)는 팀원 IP로 제한 |
| 비용 관리 | 발표가 끝나면 인스턴스 중지/삭제, 결제 알림(Billing alarm) 설정 |

**일정**
- 1주차: 배포 방식(RDS vs EC2+XE)과 AWS 계정 확정
- 6주차: 배포 환경 구축 및 첫 배포, 배포 서버에서 시연 시나리오 1회 점검
- 7주차: 최종 배포, 배포 서버로 리허설 및 발표 시연

> 선택(스트레치): GitHub Actions로 `main` 브랜치 머지 시 자동 빌드·배포(CI/CD). 시간이 부족하면 수동 배포(jar 업로드 후 재시작)로 충분합니다.

## 15. 최종 발표용 추천 기능 및 시연 시나리오

### 발표에서 강조하기 좋은 포인트
- **동시성 제어가 적용된 계좌이체**: "왜 은행 시스템에서 동시성 제어가 중요한가"를 설명하며 Lock 적용 전/후 비교 시연, 락 순서 고정으로 데드락을 예방한 설계 설명
- **거래 원장 기반 잔액 관리**: 모든 잔액 변경이 `TRANSACTION_HISTORY` 원장과 같은 트랜잭션으로 묶여 있고, "원장 합계 = 현재 잔액" 검증 쿼리로 정합성을 증명하는 구조 설명 (신뢰성 있는 설계임을 어필)
- **계좌 비밀번호 5회 오류 잠금**: 오류 → 잠금 → 관리자 해제로 이어지는 계좌 상태 전이 시연
- **본인확인(비대면 실명확인) 프로세스**: 회원가입은 즉시 완료되고, 첫 계좌 개설 시에만 본인확인 심사를 거치는 실제 은행 업무 플로우 재현 ("왜 회원가입이 아니라 계좌 개설에서 확인하는가"를 설명하면 도메인 이해도를 어필할 수 있음)
- **REST API 기반 설계**: 화면(View)과 API(백엔드)가 분리된 구조로 설계했음을 강조 (Postman/Swagger로 API 문서화해서 보여주면 가산점)
- **자산관리 리포트**: 거래내역이 자동으로 카테고리 분류되어 소비 차트로 시각화되는 모습은 발표에서 시각적 임팩트가 큼
- **대출 관리자 심사 + 상환 스케줄 계산**: 단순 CRUD가 아니라 "신청 → 관리자 심사 → 승인 시 대출금 입금·상환 스케줄 생성"이라는 업무 로직을 보여줌

### 시연 시나리오 (예시 흐름)
1. 신규 회원가입 → 바로 로그인 → 첫 입출금 계좌 개설 신청(신분증 정보·1원 인증 mock) → 계좌가 "개설대기"로 표시되는 것 확인
2. (관리자 계정으로 전환) 본인확인 심사 승인 → (회원 계정) 계좌가 "정상"으로 바뀐 것 확인 → 계좌 별명 설정
3. 입금 → 잔액 반영 확인
4. 즐겨찾기에 등록한 계좌로 이체 → 양쪽 계좌 거래내역에 반영되는 것 확인
5. **(심화) 예약이체 등록** → 지정한 시각에 자동 실행되는 것을 배치 로그로 확인
6. 적금 상품 가입 → 만기일/예상이자 확인, 목표저축 챌린지 진행률 확인
7. 거래내역 화면에서 기간별 검색/필터링 + **(심화) 카테고리별 소비 분석 차트** 시연
8. **(확장) 대출 이자 시뮬레이터**로 예상 상환액 확인 → 대출 신청 → (관리자 계정으로 전환) 대출 심사 화면에서 승인 → (회원 계정) 대출금 입금 및 상환 스케줄 조회
9. **(선택) 실시간 알림**: 다른 브라우저(또는 다른 계정)에서 내 계좌로 이체 발생 시, 알림이 화면에 즉시 표시되는 모습 시연
10. **(심화) 고객센터**에서 1:1 문의 등록 → 관리자 계정에서 답변 처리
11. 관리자 계정으로 전환 → 대시보드에서 전체 회원수/거래량/대출 현황 통계 확인, 특정 계좌 동결 처리 시연
12. (동결된 계좌로) 이체 시도 시 정상적으로 차단되는 예외 처리 시연
13. 계좌 비밀번호를 5회 틀려 계좌가 잠기는 것 확인 → 관리자 계좌 관리 화면에서 잠금 해제

> 11~12번 시나리오처럼 **정상 케이스뿐 아니라 예외/제약 조건이 의도대로 동작하는 것**을 보여주면 "단순 CRUD가 아니라 업무 로직을 이해하고 구현했다"는 인상을 강하게 줄 수 있습니다. `[심화]/[선택]` 표시가 붙은 단계(5, 7 후반부, 8~10)는 실제로 구현된 항목만 포함하고, 구현하지 못했다면 시나리오에서 자연스럽게 제외하면 됩니다.
