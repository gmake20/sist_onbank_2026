## 19p — PART 01 담당 기능 소개 (약 1분)

**이 페이지에서 전할 것:** 팀원1은 모든 파트가 쓰는 **로그인 · 권한 · 보안**의 기반을 맡았다.

**원고**

> 첫 번째 파트, 인증과 보안을 맡은 신창만입니다.
>
> 제 파트는 다른 팀원들이 만든 모든 기능의 **입구**에 해당합니다. 고객이 계좌를 보거나 이체를 하려면 먼저 로그인을 해야 하고, 직원이나 관리자가 업무 화면에 들어가려면 권한 검사를 통과해야 합니다. 그 부분을 공통 모듈로 만들었습니다.
>
> 담당 기능은 크게 여섯 가지입니다.
> 첫째, 회원가입과 로그인입니다. 고객 · 직원 · 관리자 로그인을 완전히 분리했고, 세션 기반으로 인증합니다.
> 둘째, Spring Security 권한입니다. 필터 체인을 세 개로 나누고, 직원은 책임자(MANAGER)가 일반 직원(STAFF)의 권한을 포함하도록 계층을 두었습니다.
> 셋째부터는 보안 기능입니다. 비밀번호 5회 오류 잠금, 가상 OTP 발급과 검증을 만들었고,
> 마지막으로 카카오맵을 이용한 지점 · ATM 찾기를 맡았습니다.
>
> 아래는 제가 담당한 테이블입니다. 회원, 직원, OTP 기기, 지점 테이블 등입니다.

**말할 때 주의:** 슬라이드의 "본인확인 심사", "이체한도 변경 신청"은 위 원고에서 일부러 뺐습니다. 슬라이드를 그대로 둔다면 "본인확인 심사는 설계까지 진행했고, 구현은 다음 단계입니다"라고 한마디 덧붙여 주세요.

## 20p — 구현 화면: 인증 · 보안 (약 1분)

**화면 구성 :** 왼쪽 고객 로그인 · 관리자 로그인 화면, 오른쪽 OTP 발급 화면 · OTP 앱(인증기) 화면

**원고**

> 실제 구현한 화면입니다.
>
> 왼쪽은 로그인 화면입니다. 위가 고객 로그인, 아래가 관리자 로그인입니다. 주소도 `/login`, `/admin/login`으로 다르고, 같은 아이디 비밀번호 칸처럼 보여도 서로 다른 회원 테이블을 조회합니다. 고객 로그인 화면에서는 회원가입과 비밀번호 찾기로 바로 갈 수 있습니다.
>
> 오른쪽은 보안설정의 OTP 발급 화면입니다. 발급 버튼을 누르면 10자리 일련번호와 등록 코드, QR 코드가 나옵니다. 이 등록 코드는 **딱 한 번만** 보여 주고, 화면을 벗어나면 다시 볼 수 없습니다.
>
> 이 QR 코드를 Google Authenticator 같은 휴대폰 OTP 앱으로 찍으면, 아래 그림처럼 "OnBank: 일련번호"로 등록되고 30초마다 6자리 번호가 바뀝니다. 별도의 OTP 기기 없이 일반 OTP 앱을 그대로 쓸 수 있도록 표준 방식으로 구현했습니다.

**강조 포인트 :** "한 번만 보여 준다", "일반 OTP 앱으로 등록된다"

## 21p — 핵심 구현: 권한별 로그인 분리 (약 1분 30초)

**이 페이지에서 전할 것:** 로그인 주소마다 **필터 체인 · 회원 테이블 · 권한**이 따로 있다.

**원고 (위쪽 3줄)**

> 이 페이지가 제 파트의 핵심입니다.
>
> ONBANK에는 로그인하는 사람이 세 종류입니다. 고객, 은행 직원, 시스템 관리자입니다. 이 셋을 하나의 로그인으로 처리하면 고객 계정으로 직원 화면에 들어가는 실수가 생길 수 있어서, Spring Security 필터 체인을 **세 개로 분리**했습니다.
>
> `/login`으로 들어오면 고객 필터 체인이 members 테이블에서 회원을 찾고, 로그인하면 `/mybank` 아래 고객 화면을 쓸 수 있습니다.
> `/employee/login`은 직원 필터 체인이 employee 테이블을 조회합니다. 직원은 일반 직원 STAFF와 책임자 MANAGER로 나뉘고, 책임자는 일반 직원 권한을 모두 포함합니다.
> `/admin/login`은 관리자 체인입니다. 총괄 관리자 SUPER_ADMIN이 운영(OPERATOR)과 고객지원(SERVICE) 권한을 모두 갖고, 운영과 고객지원은 서로의 권한을 갖지 않게 나눴습니다.
>
> 그리고 세 종류의 로그인 정보는 세션에 **서로 다른 이름으로 저장**합니다. 그래서 같은 브라우저에서 고객과 직원으로 동시에 로그인해도 섞이지 않습니다.
>
> 세 로그인 모두 비밀번호를 5번 틀리면 계정을 잠그고, 임시 비밀번호로 로그인하면 비밀번호를 바꾸기 전까지 다른 화면에 들어갈 수 없게 했습니다.

**아래 "본인확인 흐름" — 두 가지 중 하나를 고르세요**

- **A. 슬라이드를 그대로 둘 때 (설계로 소개)**

  > 아래는 다른 파트와 연결되는 본인확인 흐름입니다. 고객이 첫 계좌를 개설하면 본인확인을 신청하고, 직원이 승인하면 계좌가 대기에서 정상 상태로 바뀌는 구조로 **설계**했습니다. 실제 구현은 다음 단계로 남아 있습니다.

- **B. 권장 — 아래쪽을 구현된 "로그인 보안 흐름"으로 바꿀 때**

  예시 4단계 : `로그인 시도` → `비밀번호 확인 (BCrypt)` → `5회 오류 시 잠금 (LoginFailureHandler)` → `임시 비밀번호면 변경 강제 (TempPasswordFilter)`

**예상 질문**
- *왜 필터 체인을 하나로 하고 권한만 나누지 않았나요?* → 사용자 테이블과 로그인 화면, 로그인 실패 처리, 세션 저장 이름이 모두 달라서 체인을 나누는 편이 섞일 위험이 없고 각자 설정하기 쉬웠습니다.
- *JWT가 아니라 세션을 쓴 이유는?* → 은행 서비스라 강제 로그아웃이나 계정 잠금이 즉시 반영돼야 하고, Thymeleaf로 서버에서 화면을 그리는 구조라 세션이 더 맞았습니다. 서버를 늘리면 Redis로 세션을 공유하면 됩니다.

## 22p — 핵심 구현: 이메일 인증 (약 1분 30초)

**이 페이지에서 전할 것:** 비밀번호 찾기가 이메일로 가기 때문에, 가입할 때 **실제로 받을 수 있는 이메일인지** 확인한다.

**원고**

> 다음은 이메일 인증입니다.
>
> 먼저 왜 필요한지부터 말씀드리면, 비밀번호를 잊어버렸을 때 임시 비밀번호를 **가입한 이메일로** 보내 줍니다. 그런데 가입할 때 아무 이메일이나 적을 수 있다면 비밀번호를 찾을 방법이 없어집니다. 그래서 가입 단계에서 실제로 메일을 받을 수 있는 주소인지 확인합니다.
>
> 흐름은 이렇습니다. 이메일을 입력하고 인증번호 받기를 누르면 `/api/email/send`가 호출되고, SecureRandom으로 만든 6자리 번호를 메일로 보냅니다. 메일은 문자보다 늦게 올 수 있어서 유효 시간은 5분으로 두었고, 연속으로 누르는 것을 막기 위해 60초가 지나야 다시 보낼 수 있습니다.
>
> 번호를 입력하면 `/api/email/verify`에서 세션에 저장해 둔 번호와 비교합니다. 다섯 번 틀리면 번호를 폐기하고 다시 받아야 합니다. 비교할 때는 걸린 시간으로 번호를 추측하지 못하도록 고정 시간 비교를 썼습니다.
>
> 마지막으로 중요한 점은, 화면에서 인증을 통과했다고 끝나는 게 아니라 **회원가입 요청을 받을 때 서버가 한 번 더 확인**한다는 것입니다. 화면을 조작해서 인증 단계를 건너뛰어도 서버에서 가입이 거부됩니다.
>
> 이미 가입된 이메일이면 메일을 보내지 않고, 마이페이지에서 이메일을 바꿀 때도 같은 인증을 거칩니다.

**강조 포인트 :** "서버에서 한 번 더 확인", "5분 · 60초 · 5회"

**예상 질문**
- *개발 중에는 메일을 어떻게 테스트했나요?* → 메일 발송을 인터페이스(`EmailSender`)로 만들어서, 설정에 따라 실제 SMTP로 보내거나 콘솔에 출력하도록 바꿔 끼울 수 있게 했습니다.
- *인증번호를 DB가 아니라 세션에 둔 이유는?* → 5분짜리 임시 값이라 테이블을 만들 필요가 없었고, 휴대폰 인증과 같은 방식으로 맞췄습니다.

## 23p — 핵심 구현: 카카오맵 API 지점 · ATM 찾기 (약 1분)

**이 페이지에서 전할 것:** 로그인 없이 누구나 쓰는 화면, REST API로 데이터를 받아 카카오맵에 표시한다.

**원고**

> 다음은 지점 · ATM 찾기입니다.
>
> 이 화면은 고객이 아니어도 쓸 수 있어야 해서 로그인 없이 공개했습니다.
>
> 구조는 화면과 데이터를 나눴습니다. `/branches`는 화면만 보여 주고, 실제 지점 데이터는 화면이 `/api/branches`라는 REST API를 호출해서 JSON으로 받아 옵니다. 지점인지 ATM인지, 지역이나 지점 이름, 24시간 운영 여부, 입금 · 계좌개설 같은 업무별로 걸러서 검색할 수 있습니다.
>
> 받아 온 결과는 카카오맵 SDK로 지도에 표시합니다. 기본 마커 대신 CustomOverlay로 직접 핀을 만들어서, 지점은 '지', ATM은 'A'로 구분했습니다. 검색 결과가 모두 보이도록 지도 범위를 자동으로 맞춥니다.
>
> 핀을 누르면 주소, 영업시간, 전화번호, 이용 가능한 업무가 담긴 정보창이 뜨고, 왼쪽 목록에서도 같은 지점이 강조됩니다.

**예상 질문**
- *카카오맵 키가 없으면 어떻게 되나요?* → 키가 없거나 지도 로딩에 실패하면 지도 영역에 안내만 띄우고, 목록으로는 그대로 검색할 수 있습니다.
- *내 위치에서 가까운 지점을 찾을 수 있나요?* → 지금은 지역 · 이름 검색입니다. 브라우저 위치 정보로 거리순 정렬하는 것은 다음 단계입니다.

## 24p — 카카오맵 설정과 실제 화면 (약 45초)

**화면 구성 :** 위 카카오 개발자 사이트의 카카오맵 사용 설정(ON), 아래 실제 배포 서버(`scym3.cafe24.com:8000/branches`) 화면

**원고**

> 카카오맵을 쓰려면 카카오 개발자 사이트에서 앱을 등록하고, 카카오맵 사용 설정을 켜야 합니다. 여기서 받은 JavaScript 키는 GitHub에 올리지 않고, 서버의 설정 파일로 넣었습니다.
>
> 아래는 실제 배포된 서버의 화면입니다. "강남"으로 검색하면 결과 목록이 왼쪽에 나오고, 오른쪽 지도에 핀이 찍힙니다. 강남지점을 선택하면 핀이 빨간색으로 바뀌고, 정보창에 주소와 영업시간, 전화번호, 그리고 입금 · 출금 · 계좌개설 같은 이용 가능한 업무가 표시됩니다.

**시연 팁 :** 시간이 되면 실제 사이트에서 "ATM" 탭과 "24시간 운영"을 눌러 보여 주면 효과가 좋습니다.

## 25p — 핵심 구현: 가상 OTP 발급과 이체 인증 (약 1분 30초)

**이 페이지에서 전할 것:** OTP 발급 · 등록 · 분실은 팀원1, 이체할 때 OTP를 요구하는 것은 팀원2 — **두 파트가 연결되는 기능**이다.

**원고 (위쪽 3줄)**

> 다음은 가상 OTP입니다. 실제 은행처럼 일정 금액 이상 이체할 때 OTP를 요구하기 위해 만들었습니다.
>
> 먼저 발급입니다. 발급하면 OTP마다 고유한 비밀값, 시드(seed)를 만듭니다. 서버는 나중에 이 시드로 번호를 다시 계산해야 하기 때문에 비밀번호처럼 해시로 저장할 수 없고, **AES-256-GCM으로 암호화해서** DB에 저장합니다. 암호화 키는 GitHub에 올리지 않고 서버 설정으로만 넣습니다.
>
> 두 번째는 사용 등록입니다. 앱에 표시된 번호를 **연속으로 두 번** 입력해야 등록이 끝납니다. 한 번만 받으면 우연히 맞을 수도 있어서, 두 번 연속 맞춰야 실제로 기기를 가지고 있고 시계도 맞다는 걸 확인할 수 있습니다. 번호 계산은 Google Authenticator와 같은 TOTP 표준(RFC 6238)을 직접 구현했습니다.
>
> 세 번째로 휴대폰을 잃어버리면 분실 신고를 합니다. 다른 사람이 로그인된 화면에서 몰래 누르지 못하게 로그인 비밀번호를 한 번 더 확인하고, 신고하면 새로 발급받을 수 있습니다.

**원고 (아래 흐름)**

> 아래는 이체와 연결되는 흐름입니다. 팀원2가 만든 이체 기능에서 **10만 원을 넘고 다른 사람 계좌로 보낼 때** OTP가 필요하다고 판단하면, 제가 만든 `verify()`를 호출합니다. 휴대폰 시계가 조금 틀릴 수 있어서 앞뒤 30초까지는 허용하고, 10번 틀리면 OTP를 정지합니다. 통과하면 다시 팀원2의 이체가 실행됩니다.
>
> 여기서 고민했던 점이 하나 있습니다. OTP를 틀리면 이체는 취소되는데, 같은 트랜잭션 안에 있으면 **오류 횟수까지 같이 롤백돼서** 10회 정지가 동작하지 않습니다. 그래서 오류 횟수 저장을 별도 트랜잭션(REQUIRES_NEW)으로 분리했습니다. 이건 뒤에 팀원2의 트러블 슈팅과도 같은 문제입니다.
>
> 또 같은 번호를 두 번 쓰는 것도 막았습니다. 한 번 통과한 번호는 30초 안이라도 다시 쓸 수 없습니다.

**강조 포인트 :** "암호화 저장(해시 불가 이유)", "연속 2회 입력", "오류 횟수 별도 트랜잭션"

**예상 질문**
- *왜 시드를 해시가 아니라 암호화했나요?* → 해시는 되돌릴 수 없어서 서버가 번호를 계산할 수 없습니다. 그래서 되돌릴 수 있는 암호화를 쓰고 키를 코드와 분리했습니다.
- *OTP 라이브러리를 쓰지 않은 이유는?* → 알고리즘이 HMAC-SHA1과 잘라내기 몇 줄이라 직접 구현했고, RFC 6238 문서에 있는 공식 테스트 값으로 같은 번호가 나오는지 테스트로 확인했습니다.

## 부록 — 세션을 선택한 이유 (세션 vs JWT 질문 대비)

부록 표의 한 줄 답변 "즉시 로그아웃 · 계정 잠금이 중요하고 서버 렌더링 구조라 세션. 확장 시 Redis로 세션 공유"를 풀어 쓴 내용입니다.

### 1. 즉시 로그아웃 · 계정 잠금이 중요하다

**세션 방식**은 로그인 정보를 **서버**가 들고 있습니다. 브라우저는 "내 번호표는 ABC123" 같은 세션 ID만 갖고 있습니다.
- 서버에서 그 세션을 지우면 다음 요청부터 바로 로그아웃 상태가 됩니다.
- 관리자가 계정을 정지하거나 사용자가 비밀번호를 바꿨을 때 **그 순간 바로** 차단할 수 있습니다.

**JWT 방식**은 로그인 정보를 담은 토큰을 **브라우저**가 들고 있습니다. 서버는 토큰의 서명만 확인하고 따로 기록을 남기지 않습니다.
- 한 번 발급한 토큰은 만료 시간(예: 15분)이 될 때까지 서버가 취소할 방법이 없습니다.
- 그래서 계정을 정지해도 이미 발급된 토큰으로 만료될 때까지 계속 쓸 수 있습니다.

은행은 "도용이 의심되면 즉시 차단"이 아주 중요해서 세션 방식이 유리합니다.

### 2. 서버 렌더링 구조다

ONBANK는 **Thymeleaf**로 서버가 HTML을 완성해서 브라우저에 보내 주는 구조입니다.
- 이 구조에서는 브라우저가 쿠키(`JSESSIONID`)를 자동으로 보내고 Spring Security가 알아서 처리합니다. 따로 만들 것이 거의 없습니다.
- JWT는 주로 React 같은 프론트엔드나 모바일 앱이 API를 호출하는 구조에서 씁니다. 화면 쪽에서 토큰을 저장하고 매 요청 헤더에 직접 붙여야 해서, 지금 구조에서는 오히려 일만 늘어납니다.

### 3. 확장할 때는 Redis로 세션을 공유한다

세션 방식의 약점에 대한 대답입니다. 지금은 세션이 **서버(Tomcat) 메모리**에 저장되기 때문에 두 가지 문제가 있습니다.
- **서버를 2대 이상으로 늘리면:** 서버 A에서 로그인했는데 다음 요청이 서버 B로 가면, B에는 그 세션이 없어서 로그인이 풀립니다.
- **재배포하면:** 컨테이너를 새로 띄울 때 메모리가 비워지니, 접속 중이던 사용자가 모두 로그아웃됩니다.

해결 방법은 세션을 서버 메모리가 아니라 **Redis**(빠른 메모리 저장소)에 두는 것입니다.

```
현재:    브라우저 → 서버A (세션: 서버A 메모리)

확장 후: 브라우저 → 서버A ┐
                 → 서버B ┴→ Redis (세션 공유)
```

- 어느 서버로 요청이 가도 같은 Redis에서 세션을 찾으니 로그인이 유지됩니다.
- 서버를 재배포해도 세션은 Redis에 남아 있습니다.
- Spring에서는 `spring-session-data-redis` 의존성과 설정 몇 줄만 추가하면 되고, 지금 코드는 거의 바꿀 필요가 없습니다.

즉 "서버가 늘어나면 세션이 문제 아니냐"는 질문에는 **"JWT로 바꿀 필요 없이 세션 저장 위치만 Redis로 옮기면 된다"**고 답하면 됩니다.

### 발표 때 이렇게 말하면 됩니다

> "은행 서비스는 도용이 의심되면 즉시 로그아웃시키고 계정을 잠가야 하는데, 세션 방식은 서버에서 세션만 지우면 바로 차단됩니다. 또 Thymeleaf로 서버에서 화면을 그리는 구조라 세션이 더 자연스러웠습니다. 나중에 서버를 여러 대로 늘리면 세션을 Redis에 저장해서 모든 서버가 같이 쓰도록 하면 됩니다."

## 부록 — 비밀번호를 BCrypt로 저장하는 이유

부록 표의 "비밀번호 저장 → BCrypt 해시"는 **회원 비밀번호를 DB에 그대로 저장하지 않고, BCrypt라는 방식으로 해시해서 저장한다**는 뜻입니다. 코드에서는 `SecurityConfig`의 `PasswordEncoder`가 `BCryptPasswordEncoder`로 설정돼 있습니다.

### 1. 해시란

해시는 입력값을 **되돌릴 수 없는** 다른 문자열로 바꾸는 것입니다.

```
비밀번호 "abc1234!"  →  BCrypt  →  $2a$10$N9qo8uLOickgx2ZMRZoMye...
```

- 같은 비밀번호를 넣으면 맞는지 검증할 수 있습니다.
- 결과값을 보고 원래 비밀번호를 알아낼 수는 없습니다.

그래서 DB가 유출돼도 해시값만 나가고 원래 비밀번호는 드러나지 않습니다. 개발자나 관리자도 고객 비밀번호를 볼 수 없습니다.

### 2. 로그인할 때 비교하는 방법

되돌릴 수 없으니 저장된 값을 풀어서 비교하지 않습니다. **입력한 비밀번호를 같은 방식으로 다시 해시해서** 저장된 값과 맞는지 봅니다. Spring Security의 `passwordEncoder.matches(입력값, 저장된 해시)`가 이 일을 합니다. OTP 분실 신고에서 비밀번호를 다시 확인할 때도 같은 메서드를 씁니다.

### 3. SHA-256 같은 일반 해시와의 차이

**① 솔트(salt)가 자동으로 들어갑니다**
- BCrypt는 해시할 때마다 무작위 값(솔트)을 섞습니다. 그래서 두 회원이 똑같이 `abc1234!`를 써도 저장되는 값이 서로 다릅니다.
- 일반 해시는 같은 비밀번호면 결과도 같습니다. 그러면 "자주 쓰는 비밀번호 → 해시값" 표(레인보우 테이블)를 미리 만들어 두고 대조하는 공격에 바로 뚫립니다.

**② 일부러 느리게 만들어져 있습니다**
- SHA-256은 아주 빨라서, 공격자가 1초에 수십억 개의 비밀번호를 시험해 볼 수 있습니다.
- BCrypt는 계산 비용(cost)을 정할 수 있고, 기본값 10이면 한 번 계산에 수십 밀리초 정도 걸립니다.
- 로그인하는 사용자에게는 느껴지지 않을 시간이지만, 수십억 개를 대입해야 하는 공격자에게는 사실상 불가능한 시간이 됩니다.

**③ 저장값 하나에 필요한 정보가 다 들어 있습니다**

```
$2a$10$N9qo8uLOickgx2ZMRZoMye IjZAgcfl7p92ldGxad68LJZdL17lhWy
 │   │  └ 솔트 (22글자)         └ 해시 결과
 │   └ 비용(cost) 10
 └ BCrypt 버전
```

솔트를 따로 저장할 컬럼이 필요 없습니다.

### 4. 비밀번호는 해시, OTP 시드는 암호화인 이유

| | 비밀번호 | OTP 시드 |
|---|---|---|
| 방식 | BCrypt 해시 (되돌릴 수 없음) | AES-256-GCM 암호화 (키로 되돌릴 수 있음) |
| 이유 | 맞는지 **비교**만 하면 되므로 원래 값이 필요 없음 | 서버가 시드로 OTP 번호를 **다시 계산**해야 하므로 원래 값이 필요함 |

### 발표 때 이렇게 말하면 됩니다

> "비밀번호는 BCrypt로 해시해서 저장합니다. 되돌릴 수 없어서 DB가 유출돼도 원래 비밀번호는 알 수 없고, 같은 비밀번호라도 회원마다 저장값이 다르게 만들어집니다. 또 계산이 일부러 느리게 설계돼 있어서 무작위로 대입하는 공격에도 강합니다."

## 부록 — CSRF와 ONBANK의 방어

**CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)**는 사용자가 로그인해 있는 상태를 악용해서, **사용자 몰래 다른 사이트에서 요청을 보내게 만드는 공격**입니다.

### 1. 공격이 일어나는 과정

고객이 ONBANK에 로그인한 상태라고 하겠습니다. 브라우저에는 로그인 쿠키(`JSESSIONID`)가 저장돼 있습니다.

1. 고객이 같은 브라우저로 공격자가 만든 사이트(예: 이벤트 당첨 페이지)에 들어갑니다.
2. 그 페이지 안에는 눈에 보이지 않는 폼이 숨어 있습니다.
   ```html
   <form action="https://onbank.com/mybank/transfer" method="post">
     <input name="toAccount" value="공격자계좌">
     <input name="amount" value="1000000">
   </form>
   <script>document.forms[0].submit();</script>
   ```
3. 브라우저는 ONBANK로 요청을 보낼 때 **ONBANK 쿠키를 자동으로 함께 보냅니다.** 어느 사이트에서 시작된 요청인지는 따지지 않습니다.
4. 서버 입장에서는 로그인한 고객이 직접 이체를 요청한 것처럼 보입니다.

핵심은 **"쿠키는 자동으로 따라간다"**는 점입니다. 그래서 세션(쿠키) 방식을 쓰는 서비스는 CSRF 방어가 꼭 필요합니다.

### 2. 막는 방법: CSRF 토큰

서버가 화면을 줄 때 **예측할 수 없는 무작위 값(토큰)**을 폼 안에 숨겨서 넣어 둡니다.

```html
<input type="hidden" name="_csrf" value="8f3a...무작위값">
```

- 요청이 오면 서버는 이 토큰이 세션에 저장된 값과 같은지 확인하고, 다르거나 없으면 거부합니다.
- 공격자 사이트는 ONBANK 화면을 읽을 수 없으니 토큰 값을 알 수 없습니다. 쿠키는 자동으로 따라가도 토큰은 따라가지 않기 때문에 공격이 막힙니다.

### 3. ONBANK에서 하고 있는 것

| 항목 | 내용 |
|---|---|
| CSRF 보호 | Spring Security 기본값대로 **켜 둠** (끄지 않음, `SecurityConfig`) |
| 일반 폼 | `th:action`을 쓰면 Thymeleaf가 `_csrf` 토큰을 폼에 **자동으로** 넣음 (로그인, 회원가입 등) |
| 일부 폼 | `_csrf` hidden 입력을 직접 넣음 (대출 심사, 예적금 화면 등) |
| fetch API | 이메일·휴대폰 인증 API는 화면이 폼 안의 `_csrf` 값을 함께 보냄 |
| 로그아웃 | **POST로만** 허용. GET 링크로 하면 남의 사이트에 `<img src="/logout">` 한 줄만 넣어도 강제로 로그아웃시킬 수 있기 때문 |
| 토큰 오류 처리 | 로그인 화면을 띄워 둔 채 서버가 재시작되는 등 토큰이 만료되면 오류 화면 대신 로그인 화면으로 다시 보냄 |

**GET 요청은 토큰을 검사하지 않습니다.** GET은 조회만 하고 데이터를 바꾸지 않는다는 원칙 때문입니다. 그래서 `/api/branches`처럼 조회만 하는 API는 토큰 없이 호출해도 됩니다. 반대로 이체나 비밀번호 변경처럼 데이터를 바꾸는 요청은 반드시 POST로 만들어야 이 보호를 받습니다.

### 발표 때 이렇게 말하면 됩니다

> "세션 방식은 브라우저가 쿠키를 자동으로 보내기 때문에, 다른 사이트에서 몰래 이체 요청을 보내는 CSRF 공격에 노출될 수 있습니다. 그래서 Spring Security의 CSRF 보호를 끄지 않고, 모든 폼과 fetch 요청에 토큰을 함께 보내도록 했습니다. 로그아웃도 같은 이유로 POST로만 받습니다."
