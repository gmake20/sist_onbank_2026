## 작성 규칙

- 화면 ID: 화면 `S-번호`, 모달 `M-번호`
- 경로는 초안. API 명세 확정 시 함께 수정
- 연결 기능은 기능명세서(03-기능명세서.md)의 기능 ID에서 `FUNC-ADM-`을 뺀 약칭
- ★ 표시는 FDS/MON 화면. 구현 범위가 아직 미정이라 와이어프레임만 그리고 구현은 뒤로 미룬다

## 확정한 결정

- **거래/이체내역은 한 화면(S-09)에 탭으로 합친다.** 두 기능의 필터 구조가 거의 같아서 화면을 하나로 줄인다.
- **회원 상세(S-06), 대출 상세(S-13)의 탭 구성은 틀만 잡고 비워 둔다.** 다른 파트의 테이블 구조가 확정된 뒤 채운다.

- 회원 정보는 STAFF, MANAGER 모두 마스킹 없이 보여준다. 실제 은행은 마스킹하지만 모의 프로젝트라 단순화했다 (2026-10-14 사용자 판단). 발표 질문에는 "확장 과제"로 답한다.
- 거래는 고객·계좌를 검색한 뒤에만 조회한다. 전체 거래 목록은 ADMIN만 본다 (STAFF는 사용자 판단, MANAGER는 같은 기준으로 가정, 확인 필요).
- 대출은 ADMIN은 조회만, 접수는 STAFF, 최종 승인은 MANAGER (DECISIONS D-04). OPERATOR의 대출 접근은 조회만으로 유지.
- 카드 심사도 대출과 같은 방식이다 (2026-10-14 사용자 판단). 카드 심사대기 상태·심사자 컬럼은 팀원3과 협의 필요.
- 이상거래: 알림 수신은 MANAGER 이상, 처리는 ADMIN만 (01-기획서 11장). MANAGER가 탐지 상세에서 무엇을 할 수 있는지(연락 기록 입력 포함 여부, 버튼 숨김/비활성)는 재검토 필요 (2026-10-15).
- 활동 로그는 SUPER_ADMIN 전용으로 확정했다.
- *OPERATOR는 계정 요청 처리 담당 (2026-10-15 결정, 01-기획서 5.1). 잠금 해제는 모든 계정, 임시 비밀번호 재발급은 SUPER_ADMIN 계정만 제외. 최고 관리자는 1명이라 계정 생성 화면에서 SUPER_ADMIN을 만들 수 없다.
- 역할별 메뉴·API 제한(AUT-004)은 심화 단계에서 적용한다.
- 직원·관리자 로그인 분리 (2026-10-15, D-02): STAFF·MANAGER가 쓰는 화면은 `/employee/**` 경로가 된다. 1장 경로와 이 표는 팀원1과 업무 배분을 확정한 뒤 고친다 (`ROLE-관리자·직원-권한정리.md`).
