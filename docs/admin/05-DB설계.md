# DB 설계

> 출처: `07-admin_ddl.sql` (MySQL 8.0.16+ 기준, 초안 v0.8). 컬럼 타입·제약은 이 DDL 기준이다.
> 기능과 컬럼의 대응은 03-기능명세서.md 3장 "관련 테이블 초안" 참고.
> 이번에는 **관리자 파트 소유 테이블 6개만** 적었다. 다른 파트 테이블(members 등)은 컬럼을 확인한 뒤 추가한다.

## 이름 규칙 (2026-10-14)

- 테이블명·컬럼명은 **소문자**. 팀원1(`01_auth_ddl.sql`)·팀원2 DDL과 같다.
- FK 컬럼명은 **참조하는 컬럼명과 같게** 쓴다. 같은 테이블을 여러 의미로 참조하거나 의미를 밝혀야 하면 앞에 역할을 붙인다 (예: `assigned_admin_id`. 팀원1의 `reviewed_employee_id`와 같은 방식).
- 제약·인덱스 이름(`PK_`, `FK_`, `CK_`, `IDX_`)과 저장되는 코드값(`ACTIVE`, `UNCHECKED` 등)은 대문자 그대로 둔다.

## ERD

텍스트 ERD (실제 FK는 `FK` 표시, 점선 관계는 FK 없음)

```text
admin 1 ──< N fds_detection             FK_FDS_DET_ADMIN         (assigned_admin_id, 배정 전 NULL)
admin 1 ──< N fds_handling_history      FK_FDS_HIS_ADMIN         (admin_id)
admin 1 ──< N admin_login_log           FK_ADMIN_LOGIN_ADMIN     (admin_id, 없는 아이디 시도는 NULL)
fds_detection 1 ──< N fds_handling_history   FK_FDS_HIS_DETECTION (detection_id)

account             1 ──< N fds_detection   FK_FDS_DET_ACCOUNT   (account_id, 팀원2 소유)
transaction_history 1 ──< N fds_detection   FK_FDS_DET_HISTORY   (transaction_history_id, 팀원2 소유)
  → 이체 정보는 transaction_history에서 따라감 (연결 컬럼은 아래 메모 참고, FK 없음)

admin_log.actor_id               : actor_type(ADMIN/EMPLOYEE)에 따라 admin 또는 employee를 가리켜서 FK 없음
admin_notification.recipient_id  : recipient_type(ADMIN/EMPLOYEE)에 따라 admin 또는 employee를 가리켜서 FK 없음
admin_log.target_id              : target_type에 따라 대상 테이블이 달라서 FK 없음
admin_notification.target_id     : 탐지 ID 등, FK 없음
```

## 테이블 목록

`내 파트 사용` 칸에 관리자 파트가 사용하는 테이블을 표시한다. 기능 문서에서는 이 파일로 링크만 건다.

| 테이블 | 설명 | 소유 | 내 파트 사용 | 사용하는 기능 분류 |
|---|---|---|---|---|
| admin | 백오피스 관리자 계정 (employee와 별개 테이블. 관리자는 `/admin/login`, 직원은 `/employee/login`으로 따로 로그인, D-02) | 관리자 (팀원1 협의) | O | AUT, ACT |
| employee (참조만) | 창구 직원. `/employee/login`으로 따로 로그인 (로그인 처리는 팀원1, D-02) | 팀원1 | 조회 | AUT |
| admin_log | 관리자·직원 활동 로그 (감사 로그) | 관리자 | O | LOG, 상태를 바꾸는 모든 기능 |
| fds_detection | 이상거래 탐지 건과 처리 단계 (이체·출금) | 관리자 | O | FDS, MON |
| fds_handling_history | 탐지 건 처리 이력, 고객 연락 결과 | 관리자 | O | FDS |
| admin_notification | 관리자 알림함 | 관리자 | O | MON |
| admin_login_log | admin 로그인 이력 (2026-10-14 추가) | 관리자 | O | AUT, LOG |
| employee_login_log (참조만) | 직원 로그인 이력. 활동 로그 화면에서 조회만 | 팀원1 | 조회 | LOG |
| account (참조만) | 계좌 | 팀원2 | 조회, FK 대상 | FDS, ACC |
| account_transfer (참조만) | 이체 | 팀원2 | 조회 | FDS, TRX |
| transaction_history (참조만) | 거래내역 (입금·출금) | 팀원2 | 조회, FK 대상 | FDS, TRX |

## 테이블 정의

공통: `ENGINE=InnoDB`, `utf8mb4`

### admin
백오피스 관리자 계정. 로그인은 이 테이블과 employee(팀원1) 두 곳에서 하며, 입력값으로 admin → employee 순서로 조회한다. (FUNC-ADM-AUT-001, ACT-001~004)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| admin_id | BIGINT | PK, AUTO_INCREMENT | 관리자 번호 |
| login_id | VARCHAR(50) | NOT NULL, UNIQUE | 로그인 아이디 |
| password | VARCHAR(100) | NOT NULL | BCrypt 해시(60자) |
| name | VARCHAR(50) | NOT NULL | 이름 |
| role | VARCHAR(20) | NOT NULL, CHECK | SUPER_ADMIN / OPERATOR / SERVICE. 기본값 없음, 계정 생성 시 반드시 지정 |
| status | VARCHAR(10) | NOT NULL, 기본 ACTIVE, CHECK | ACTIVE / INACTIVE / LOCKED |
| temp_pw_yn | CHAR(1) | NOT NULL, 기본 'Y', CHECK | 임시 비밀번호 여부. Y면 첫 로그인 시 변경 강제 |
| login_fail_count | TINYINT | NOT NULL, 기본 0 | 5회 실패 시 LOCKED |
| last_login_at | DATETIME | NULL | 마지막 로그인 일시 |
| created_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 생성 일시 |

### admin_log
관리자(admin)와 창구 직원(employee)이 한 모든 상태 변경 기록. 수정·삭제 기능을 만들지 않는다. (FUNC-ADM-LOG-001, 002)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| log_id | BIGINT | PK, AUTO_INCREMENT | 로그 번호 |
| actor_type | VARCHAR(10) | NOT NULL, CHECK | ADMIN / EMPLOYEE. 작업한 사람이 속한 테이블 |
| actor_id | BIGINT | NOT NULL | admin_id 또는 employee_id. 두 테이블을 가리키므로 FK 없음 |
| action_type | VARCHAR(50) | NOT NULL | 작업 유형. `대상_동작` 형식 (예: ACCOUNT_FREEZE). 전체 목록은 features/LOG-활동로그.md |
| target_type | VARCHAR(30) | NOT NULL | 대상 종류 = 바꾼 행이 있는 테이블 (ACCOUNT / ADMIN / EMPLOYEE / PRODUCT / LOAN / FDS_DETECTION / MEMBER / CARD / NOTICE / FAQ / INQUIRY). 목록은 features/LOG-활동로그.md |
| target_id | VARCHAR(50) | NOT NULL | 대상 ID. 대상이 여러 테이블이라 FK 없음 |
| before_value | VARCHAR(500) | NULL | 변경 전 값 |
| after_value | VARCHAR(500) | NULL | 변경 후 값 |
| reason | VARCHAR(200) | NULL | 사유 |
| request_ip | VARCHAR(45) | NULL | 요청 IP (IPv6 대비 45자) |
| created_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 기록 일시 |

인덱스: `IDX_ADMIN_LOG_ACTOR`(actor_type, actor_id), `IDX_ADMIN_LOG_CREATED`(created_at), `IDX_ADMIN_LOG_TARGET`(target_type, target_id)

### fds_detection
룰 기반 이상거래 탐지 건. 이체와 이체가 아닌 출금을 둘 다 탐지한다 (2026-10-14). 이체도 transaction_history에 출금 행이 남으므로 근거는 transaction_history_id 하나로 기록한다 (2026-10-15, DECISIONS D-09). (FUNC-ADM-FDS-001~005)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| detection_id | BIGINT | PK, AUTO_INCREMENT | 탐지 번호 |
| account_id | BIGINT | NOT NULL, FK → account(account_id) | 대상 계좌 (출금 계좌) |
| transaction_history_id | BIGINT | NOT NULL, FK → transaction_history(transaction_history_id) | 탐지 근거가 된 거래내역의 출금 행 (이체도 출금 행으로 기록됨) |
| rule_code | VARCHAR(30) | NOT NULL | 탐지 규칙 구분 |
| detail | VARCHAR(500) | NULL | 판정 근거(횟수, 금액 등) |
| status | VARCHAR(20) | NOT NULL, 기본 UNCHECKED, CHECK | UNCHECKED / ASSIGNED / CONTACTING / NORMAL_CONFIRMED / FRAUD_ACTION |
| assigned_admin_id | BIGINT | NULL, FK → admin(admin_id) | 담당 관리자. 배정 전에는 NULL |
| assigned_at | DATETIME | NULL | 배정 일시 |
| closed_at | DATETIME | NULL | 종료 일시 |
| detected_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 탐지 일시 |

인덱스: `IDX_FDS_DET_STATUS`(status, detected_at), `IDX_FDS_DET_ASSIGNED`(assigned_admin_id), `IDX_FDS_DET_ACCOUNT`(account_id), `IDX_FDS_DET_HISTORY`(transaction_history_id)

### fds_handling_history
탐지 건의 단계가 바뀔 때마다 남는 처리 이력. 고객 연락 결과도 여기에 기록한다. (FUNC-ADM-FDS-005, 006)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| history_id | BIGINT | PK, AUTO_INCREMENT | 이력 번호 |
| detection_id | BIGINT | NOT NULL, FK → fds_detection | 탐지 번호 |
| admin_id | BIGINT | NOT NULL, FK → admin | 처리한 관리자 |
| stage | VARCHAR(20) | NOT NULL, CHECK | 변경된 단계 (fds_detection.status와 같은 5개 값) |
| memo | VARCHAR(500) | NULL | 메모 |
| contact_at | DATETIME | NULL | 고객 연락 일시. 연락 단계에서만 입력 |
| contact_method | VARCHAR(20) | NULL | 연락 방법 (전화 등) |
| contact_result | VARCHAR(30) | NULL, CHECK | CONFIRMED_BY_CUSTOMER / NOT_CUSTOMER / NO_ANSWER |
| created_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 기록 일시 |

인덱스: `IDX_FDS_HIS_DETECTION`(detection_id, created_at), `IDX_FDS_HIS_ADMIN`(admin_id)

### admin_notification
관리자·창구 직원 알림함. 받는 사람은 admin 또는 employee. WebSocket 알림을 놓쳐도 여기서 확인한다. (FUNC-ADM-MON-001, 005)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| notification_id | BIGINT | PK, AUTO_INCREMENT | 알림 번호 |
| recipient_type | VARCHAR(10) | NOT NULL, CHECK | ADMIN / EMPLOYEE. 받는 사람이 속한 테이블 |
| recipient_id | BIGINT | NOT NULL | admin_id 또는 employee_id. 두 테이블을 가리키므로 FK 없음 |
| type | VARCHAR(30) | NOT NULL | 알림 종류 (예: FDS_DETECTED) |
| target_id | BIGINT | NULL | 탐지 ID 등. FK 없음 |
| message | VARCHAR(300) | NOT NULL | 알림 내용 |
| read_at | DATETIME | NULL | 읽음 일시. NULL이면 미확인 |
| created_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 생성 일시 |

인덱스: `IDX_ADMIN_NOTI_RECIPIENT`(recipient_type, recipient_id, read_at, created_at)

### admin_login_log
admin 로그인 이력. 추가만 하고 수정·삭제하지 않는다. 팀원1의 `employee_login_log`와 같은 모양이라 두 목록을 합쳐 볼 수 있다. (FUNC-ADM-AUT-001에서 기록)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| login_log_id | BIGINT | PK, AUTO_INCREMENT | 이력 번호 |
| admin_id | BIGINT | NULL, FK → admin | 존재하지 않는 아이디로 시도한 경우 NULL |
| login_id_input | VARCHAR(50) | NOT NULL | 입력한 아이디 (50자 초과는 잘라서 저장) |
| success_yn | CHAR(1) | NOT NULL, CHECK | Y / N |
| fail_reason | VARCHAR(30) | NULL, CHECK | BAD_CREDENTIALS / LOGIN_LOCKED / INACTIVE / UNKNOWN_ID. 성공이면 NULL, 실패면 필수 |
| ip_address | VARCHAR(45) | NOT NULL | 요청 IP |
| user_agent | VARCHAR(500) | NULL | 브라우저 정보 |
| login_at | DATETIME | NOT NULL, 기본 CURRENT_TIMESTAMP | 로그인 시도 일시 |

인덱스: `IDX_ADMIN_LOGIN_ADMIN`(admin_id, login_at), `IDX_ADMIN_LOGIN_AT`(login_at)

## 관계 / 제약 메모

- 상태값은 DDL에서 **영문 코드**를 쓴다. 기능명세서·요구사항정의서는 한글로 적혀 있다.

| 한글 (문서) | 코드 (DDL) |
|---|---|
| 활성 / 비활성 / 잠금 (admin.status) | ACTIVE / INACTIVE / LOCKED |
| 미확인 | UNCHECKED |
| 담당 확인 | ASSIGNED |
| 고객 연락 중 | CONTACTING |
| 정상 거래 확인 | NORMAL_CONFIRMED |
| 사기 의심 조치 | FRAUD_ACTION |
| 본인 거래 확인 / 본인 아님 / 연락 안 됨 | CONFIRMED_BY_CUSTOMER / NOT_CUSTOMER / NO_ANSWER |

- 탐지 단계 전이 순서: 미확인 → 담당 확인 → 고객 연락 중 → 정상 거래 확인 또는 사기 의심 조치 (03-기능명세서.md 2.13 참고). 전이 순서는 DDL의 CHECK로 막지 않고 애플리케이션에서 검사한다.
- admin_log는 상태를 바꾸는 기능과 같은 트랜잭션에서 기록한다 (03-기능명세서.md 공통 사항).
- CHECK 제약은 MySQL 8.0.16 이상에서만 적용된다. 공용 DB는 8.0.46 (2026-10-15 사용자 조회 결과).
- 공용 DB 생성 (2026-10-15): 사용자가 Workbench에서 v0.8 DDL로 관리자 테이블 6개 생성. 생성 후 INFORMATION_SCHEMA 조회로 FK 6개·CHECK 11개가 DDL과 일치함을 확인 (사용자 조회, Claude가 결과 대조). 로컬 테스트 스키마에는 아직 실행 안 함.
- 실행 순서: 팀원2의 account, transaction_history 테이블(PK 포함)이 먼저 있어야 fds_detection의 FK가 걸린다. 팀원2 DDL은 팀 레포 `project/onbank/src/main/resources/db/03_account_ddl.sql` (2026-10-16 이동, 옛 `docs/schema-team2-mysql.sql`은 삭제됨). 실행 순서 01 → 03 → 02.
- FK 대상 테이블명·컬럼명은 팀원2 DDL(당시 `docs/schema-team2-mysql.sql`, 현재 `resources/db/03_account_ddl.sql`)·엔티티와 일치함을 2026-10-15 확인. 공용 DB에 테이블이 만들어진 것은 사용자가 확인함.
- 이체 정보 연결 (2026-10-16 갱신, 확정 확인 필요): `transaction_history.account_transfer_id` 계획은 팀원2 데이터 사전에서 빠졌다. 이체 1건의 `account_transfer` 1행과 `transaction_history` 2행이 같은 `transaction_sqno`를 저장한다(팀원2 `AccountTransferService.java` 101~115줄). DB UNIQUE는 없고 생성기가 코드로 중복을 막는다. 01-기획서 11장 "팀원2 협의 목록" 5번.
- 이체 1건 = transaction_history 2행(출금·입금)이라, FDS는 출금 행만 근거로 쓴다. 출금 행은 `transaction_type` = `WITHDRAWAL`(현금 출금)·`TRANSFER_OUT`(이체)로 구분한다(팀원2 `TransactionType.java` 7~10줄, 2026-10-16 확인). DDL CHECK는 없음 → 01-기획서 11장 "팀원2 협의 목록" 4번.
- 계좌 상태 이력은 별도 테이블 없이 admin_log로 남긴다 (2026-10-15, DECISIONS D-10). 동결·해제 때 action_type=ACCOUNT_FREEZE / ACCOUNT_UNFREEZE, target_type=ACCOUNT, target_id=account_id, before_value·after_value=상태값. 현재 상태는 `account.account_status`.
- 다른 파트 테이블(members, loan, product 등)은 컬럼 확인 후 추가 예정.
